# 商品搜索链路逻辑更新的具体实现方案

> 文档状态：目标实现方案，尚未实施  
> 编写日期：2026-07-22  
> 适用范围：Globuy 商品意图识别、实时 Provider 采集、MySQL 商品持久化、OpenSearch 混合检索、AgentLoop 与 AG-UI 前端进度展示  
> 当前事实：现有 `globuy-products` 主要包含 1000 条耳机离线快照；本文描述的是扩展到任意商品品类的目标链路，不代表当前代码已经具备实时全品类搜索能力。

## 1. 背景与问题

当前 `ItemSearch` 只在本地 OpenSearch 商品别名 `globuy-products` 中执行 BM25 与冻结
`BAAI/bge-m3` Dense Vector 的无权重 RRF 混合检索。现有索引数据主要来自淘宝、京东、抖音
三个平台的 1000 条耳机离线快照，因此：

- 用户询问耳机以外的品类时，本地索引通常没有可用候选；
- 直接在空索引上做向量检索不能创造真实商品，也不能满足全品类购物需求；
- 如果每次新品类对话都同步采集约 1000 条商品，API 调用次数、向量计算和用户等待时间过高；
- 仅在任务结束时返回结果，用户无法区分“系统正在工作”和“页面卡住”；
- Provider 响应、业务数据库、检索索引和 Agent 工具之间尚未形成一条可复用的在线补库链路。

本方案将商品搜索改为“先理解意图，再检查目录覆盖，必要时按需补充约 60～100 条候选，最后执行
本地混合检索”，并用 AG-UI 事件实时向前端展示可理解的进度。

## 2. 目标与非目标

### 2.1 目标

1. 支持用户在对话中查询耳机以外的任意可合法搜索商品品类。
2. Agent 在调用商品搜索前先得到结构化购物意图，至少明确品类和主搜索词。
3. 优先复用 MySQL/OpenSearch 中仍然新鲜且覆盖充足的商品目录。
4. 缓存不足时，通过 Provider 从淘宝、京东、抖音按需获取真实候选。
5. 三个平台合计以 100 条有效去重候选为软目标，以 60 条为可用下限，以 120 条为硬上限。
6. API 数据先进入 MySQL 权威商品库，再通过 Outbox 增量投影到 OpenSearch。
7. 只对新增商品或语义文本发生变化的商品生成向量；价格、销量等变化不重复计算向量。
8. 保持当前 ItemSearch 的 BM25 + BGE-M3 + RRF、单平台召回域和融合后结构化过滤契约。
9. 采集、标准化、入库、索引和混合检索过程均产生可重放的 AG-UI 事件。
10. Provider 部分失败、超时或达到预算时如实返回 `partial`，不伪造商品或实时价格。

### 2.2 非目标

- 不训练或微调 Query/User/Item 编码模型。
- 不将 OpenSearch 替换为其他向量数据库。
- 不让 LLM 直接访问 Provider Token、写 MySQL 或操作 OpenSearch。
- 不在一次普通对话中抓取完整平台目录。
- 不保证每次都精确获得 100 条；100 是软目标，不是返回结果的阻塞条件。
- 不把搜索快照描述为实时库存、官方推荐或始终有效的价格。
- 首版不批量调用商品详情、评论或 SKU 接口；搜索结果不能提供的字段保持 `null`。
- 不把实时 Provider 采集新增为第十个 LLM 业务工具。

## 3. 必须保持的项目契约

本次更新不得破坏以下固定边界：

| 范围 | 固定契约 |
|---|---|
| Agent 工具 | 保持九个业务工具；`dispatch_tool` 仍是同质 fork 元工具 |
| 数据权威源 | MySQL `Product/Offer/OfferObservation/SourceSnapshot` 是业务事实来源 |
| 检索投影 | OpenSearch 是商品全文与向量检索投影，不是唯一事实库 |
| Dense Embedding | 冻结 `BAAI/bge-m3`，1024 维、归一化 |
| ItemSearch | 单一商品索引，BM25 + Dense Vector，通过无权重 RRF 融合 |
| 召回过滤 | `platform` 在两路召回前过滤；价格、币种、评分、销量和属性在 RRF 后过滤 |
| 真实性 | Provider 未配置返回 `not_configured`；失败不得生成占位商品 |
| 流式任务 | HTTP 202 启动、WebSocket 订阅、可取消、sequence 重放与终态清理 |
| 测试 | 自动测试不得调用真实付费模型或付费商品 Provider |

实时采集应当实现为 `ItemSearch` 下层的应用服务，而不是新的 LLM 工具：

```text
AgentLoop
  -> item_search(query, platform, top_k, filters)
      -> CatalogCoverageService
      -> CatalogHydrationService（需要时）
          -> ProductProvider
          -> MySQL
          -> Product Outbox
          -> OpenSearch
      -> ProductSearchService
```

## 4. 目标总链路

```text
用户提交购物需求
    |
    v
Think / Planner 提取 ShoppingIntent
    |
    +-- 品类不明确或硬约束冲突 --> ChatFallback 澄清，禁止付费搜索
    |
    v
ItemSearch（一个平台一个调用；多平台由同质 fork 并行）
    |
    v
CatalogCoverageService 检查当前品类/查询范围
    |
    +-- 缓存新鲜且数量充足 --> 直接混合检索
    |
    +-- 缓存不足/过期 ------> CatalogHydrationService
                                  |
                                  +-- 淘宝 Provider 分页
                                  +-- 京东 Provider 分页
                                  +-- 抖音 Provider 分页 + searchId
                                  |
                                  v
                              标准化、硬过滤、去重
                                  |
                                  v
                              MySQL 事务 upsert
                                  |
                                  v
                              Outbox 增量投影
                                  |
                                  v
                              批量向量化 + OpenSearch bulk
    |
    v
OpenSearch BM25 + BGE-M3 + RRF
    |
    v
ItemPicker -> PriceCompare -> ShoppingSummary
```

## 5. 购物意图契约

### 5.1 `ShoppingIntent`

Think/Planner 在任何付费商品搜索前应形成下列结构化状态：

```json
{
  "intent": "product_search",
  "category_key": "air_fryer",
  "category_name": "空气炸锅",
  "primary_query": "家用空气炸锅",
  "query_variants": ["小容量空气炸锅"],
  "platforms": ["taobao", "jingdong", "douyin"],
  "filters": {
    "min_price": null,
    "max_price": 600,
    "currency": "CNY",
    "min_rating": null,
    "min_sales": null,
    "attribute_equals": {}
  },
  "hard_constraints": ["适合三口之家"],
  "soft_preferences": ["容易清洗"],
  "needs_clarification": false,
  "clarification_question": null
}
```

### 5.2 意图提取规则

- `category_name` 必须是用户要购买的商品类型，不得使用“礼物”“家居”“数码”等过宽概念。
- `category_key` 是稳定归一化键；同义表达应映射到同一个键，例如“空气炸锅机”和“空气炸锅”。
- `primary_query` 用于 Provider 第一轮检索，应短、具体并包含品类核心词。
- `query_variants` 首轮最多 2 个，只有主搜索词覆盖不足时才启用，避免重复付费。
- 预算、币种、平台和硬属性从用户原话中提取；未知字段不得猜测。
- 品类不明确、用户只说“帮我买个礼物”、预算/用途明显冲突时，先通过 `ChatFallback` 追问。
- 闲聊、知识问答或已有商品链接详情查询不进入本链路。

### 5.3 澄清门禁

满足任一条件时不得调用 Provider：

1. `needs_clarification=true`；
2. `category_key/category_name/primary_query` 任一为空；
3. 平台列表为空；
4. 价格范围非法；
5. 用户明确要求暂停或取消；
6. Provider 数据持久化/展示授权不满足当前部署要求。

## 6. 目录范围与缓存覆盖

### 6.1 `CatalogScope`

缓存不能只按品类判断，否则“手机”缓存可能无法覆盖“折叠屏小屏手机”。逻辑范围至少包含：

```json
{
  "category_key": "air_fryer",
  "normalized_query": "家用空气炸锅",
  "platform": "jingdong",
  "currency": "CNY",
  "provider": "justone",
  "scope_version": "catalog-scope-v1"
}
```

范围键建议取规范 JSON 的 SHA-256 摘要，不包含 Token、用户 ID 或会话 ID。不同用户对同一公共商品
范围可以复用缓存；用户长期偏好只在后续筛选阶段使用，不能污染公共商品目录。

### 6.2 覆盖检查

`CatalogCoverageService` 返回：

```json
{
  "status": "sufficient",
  "scope_id": "scope_xxx",
  "fresh_count": 31,
  "platform": "jingdong",
  "newest_captured_at": "2026-07-22T12:00:00Z",
  "freshness_seconds": 1800,
  "refresh_required": false,
  "reason": "fresh_and_sufficient"
}
```

覆盖状态：

| 状态 | 含义 | 行为 |
|---|---|---|
| `sufficient` | 新鲜候选数量达到该平台最低覆盖 | 直接本地检索 |
| `thin` | 有数据但数量不足 | 补页后检索；超时可返回 partial |
| `stale` | 有数据但超过新鲜度 | 优先刷新；达到软时限可使用带快照提示的旧数据 |
| `missing` | 没有该范围数据 | 必须采集或返回 not_configured |
| `refreshing` | 另一个任务正在补充同一范围 | 复用同一任务进度，禁止重复付费 |

首版新鲜度应配置化，例如 `GLOBUY_CATALOG_FRESHNESS_SECONDS`；文档不把具体时长写死为业务事实。

## 7. 动态候选数量与停止算法

### 7.1 数量契约

| 参数 | 目标值 | 说明 |
|---|---:|---|
| `minimum_usable_total` | 60 | 达到后允许在软时限触发时开始检索 |
| `target_total` | 100 | 三平台合计有效去重候选软目标 |
| `hard_cap_total` | 120 | 任何普通对话不得继续扩张的硬上限 |
| `minimum_per_platform` | 15 | 平台正常可用时的最低软覆盖 |
| `target_per_platform` | 约 25～40 | 按真实分页、去重率动态分配，不要求严格平均 |

“有效候选”指完成以下处理后的结果：

- Provider 业务码成功；
- 商品 ID、标题、平台、商品链接和合法价格满足最小 Schema；
- 明显配件、无关品类和重复商品已剔除；
- 符合用户明确的硬价格/品类约束；
- 不使用模型补造缺失字段。

### 7.2 分页策略

1. 三个平台先各请求第一页。
2. 三个平台分支可受控并发；每个平台内部必须顺序翻页。
3. 抖音后续页必须携带上一成功响应的 `searchId`。
4. 每完成一页立即标准化、去重、更新覆盖计数和发布进度事件。
5. 总量不足时优先补充当前有效候选最少的平台。
6. 主词连续两页新增率过低时，启用最多一个 `query_variant`，并重置该平台分页游标。
7. 某平台连续无新增、没有更多页、达到平台调用上限或不可用时停止该平台分支。

### 7.3 正常停止条件

满足以下任一条件即停止采集：

- 有效去重总数达到 `target_total=100`，且所有可用平台均已完成至少一页；
- 有效去重总数达到 `minimum_usable_total=60`，所有可用平台达到软最低覆盖，且触发响应软时限；
- 总数达到 `hard_cap_total=120`；
- 所有平台没有更多结果或无法再产生新增候选；
- 用户取消任务；
- 达到调用次数、费用、每日配额或任务硬时限。

平台不可用时不要求强行达到三平台最低覆盖。只要其他平台达到可用下限，就返回 `partial` 并明确
缺失平台；如果总量也不足，则返回较少的真实结果或 `not_configured/error`，不得用无关商品补齐。

### 7.4 伪代码

```python
async def ensure_catalog(intent, platform):
    coverage = await coverage_service.inspect(intent, platform)
    emit("catalog_cache_checked", coverage)
    if coverage.is_sufficient:
        return coverage

    async with singleflight(coverage.scope_id):
        cursor = coverage.resume_cursor
        while not stop_policy.reached():
            page = await provider.search(
                platform=platform,
                keyword=current_keyword,
                cursor=cursor,
                filters=provider_supported_filters(intent.filters),
            )
            normalized = normalize_and_validate(page.items)
            accepted = deduplicate_and_filter(normalized, intent)
            await repository.upsert_batch(page.snapshot, accepted)
            await outbox.publish_pending()
            stop_policy.observe(platform, page, accepted)
            emit("catalog_fetch_progress", stop_policy.public_progress())
            cursor = page.next_cursor

        return await coverage_service.inspect(intent, platform)
```

### 8.1 通用接口

```python
class ProductProvider(Protocol):
```


### 8.3 错误映射

| Provider 业务码 | 内部状态 | 是否自动重试 | 用户可见语义 |
|---:|---|---|---|
| `0` | `ok` | 不适用 | 本页获取成功 |
| `100` | `not_configured` | 否 | 商品数据服务认证不可用 |
| `301` | `provider_error` | 最多一次、带退避且受预算控制 | 当前平台暂时采集失败 |
| `302` | `rate_limited` | 延迟重试或结束该平台 | 当前平台请求过快 |
| `303` | `quota_exceeded` | 否 | 今日额度已用完 |
| `400` | `invalid_request` | 否 | 搜索参数不被支持 |
| `500` | `provider_error` | 最多一次或结束 | 数据服务内部错误 |
| `600` | `not_configured` | 否 | 当前 Token 无接口权限 |
| `601` | `not_configured` | 否 | 账户余额不足 |
| `602` | `not_configured` | 否 | Token 消费上限已达到 |

Token 只能由服务端配置读取，不能进入事件、日志、MySQL原始请求 URL、OpenSearch或前端。

## 9. 并发、限流、预算和幂等

### 9.1 并发模型

- 淘宝、京东、抖音三个分支可以并行启动，以降低总体等待时间。
- 单平台只允许一个活跃分页请求，确保页码/searchId顺序和可恢复性。
- Provider 客户端使用共享 `asyncio.Semaphore` 和平台级限流器。
- 同一 `CatalogScope` 使用 singleflight：第一个任务负责采集，后续任务订阅其进度并复用结果。
- 取消根 run 时，必须取消等待中的 Provider 请求、分页循环、批量入库和向量化任务。

### 9.2 预算门禁

新增配置建议：

```dotenv
GLOBUY_PRODUCT_PROVIDER=none
GLOBUY_JUSTONE_BASE_URL=https://api.justoneapi.com
GLOBUY_JUSTONE_TOKEN=
GLOBUY_CATALOG_MINIMUM_TOTAL=60
GLOBUY_CATALOG_TARGET_TOTAL=100
GLOBUY_CATALOG_HARD_CAP_TOTAL=120
GLOBUY_CATALOG_MINIMUM_PER_PLATFORM=15
GLOBUY_CATALOG_MAX_SUCCESS_CALLS_PER_RUN=12
GLOBUY_CATALOG_MAX_ATTEMPTS_PER_RUN=20
GLOBUY_CATALOG_SOFT_DEADLINE_SECONDS=20
GLOBUY_CATALOG_HARD_DEADLINE_SECONDS=60
GLOBUY_CATALOG_FRESHNESS_SECONDS=86400
GLOBUY_PROVIDER_MAX_CONCURRENCY=3
GLOBUY_PROVIDER_PER_PLATFORM_CONCURRENCY=1
```

具体默认值在实施时通过低成本烟雾测试确认；这里的调用和时限值是目标初始配置，不是已验证的
Provider 性能承诺。费用上限只有在获得真实单价后才能启用金额门禁，否则先使用成功调用次数门禁。

### 9.3 请求幂等

`request_key` 至少由以下字段稳定生成：

```text
provider + platform + normalized_keyword + page/cursor + provider_filters + scope_version
```

- 同一请求成功响应应优先复用，禁止网络重试导致重复付费。
- 预留请求但没有响应时不得自动重发，必须由明确恢复策略处理。
- 原始响应落盘或入库前必须递归脱敏。
- SourceSnapshot 保存请求摘要、响应哈希、采集时间和状态，不保存 Token。

## 10. 数据标准化与持久化

### 10.1 写入顺序

```text
ProviderPage
  -> SourceSnapshot
  -> Product upsert
  -> Offer upsert
  -> OfferObservation insert
  -> OutboxEvent insert
  -> transaction commit
```

所有步骤在同一 MySQL 事务中完成。事务失败时不得单独更新 OpenSearch。

### 10.2 身份与去重

- Offer 级稳定 ID：`platform + source_item_id`。
- Product 首版仍可以一条平台商品对应一个 Product；跨平台同款合并需要独立的规格对齐证据。
- 同一页、跨页、跨关键词先按平台商品 ID 去重。
- 不得仅按标题相似度把不同 SKU 合并为同一商品。
- 同一商品再次采集时更新 Offer 当前字段并新增 Observation，不重复创建 Product/Offer。

### 10.3 字段真实性

- `price=null` 不转换为 0；普通候选若没有可用价格可拒绝进入本次混合检索，但可保留原始快照用于审计。
- `rating` 和 `sales` 缺失时保持 `null`。
- 评分比例与五星评分必须通过 `rating_scale/rating_type` 区分。
- `stock_status` 未由 Provider 提供时保持 `null`。
- `captured_at/last_seen_at/provider_query/category_key` 必须保留，用于新鲜度与来源审计。

### 10.4 建议的数据扩展

在不破坏现有 Product/Offer 边界的前提下，增加或补齐：

| 位置 | 字段 | 用途 |
|---|---|---|
| Product | `category/category_key/category_path` | 品类归一和检索范围 |
| Product | `semantic_hash` | 判断是否需要重新生成向量 |
| Offer | `last_seen_at` | 新鲜度和陈旧候选过滤 |
| SourceSnapshot | `provider_query/scope_id/page/cursor/status` | 请求审计和断点恢复 |
| 新逻辑实体 | `CatalogScope` | 公共目录覆盖、数量和最新状态 |
| 新逻辑实体 | `CatalogHydrationRun` | 单次补库阈值、平台进度和终态 |

具体采用新表还是扩展现有 JSON metadata，应在迁移设计阶段根据查询和唯一约束决定。

## 11. 向量化与 OpenSearch 增量投影

### 11.1 语义文本

继续只使用标题和稳定属性，例如：

- 品牌、型号、标准品类；
- 核心规格；
- 使用场景；
- 连接方式、容量、尺寸等品类稳定属性。

价格、销量、评分、促销、店铺和采集时间不得写入语义文本。

### 11.2 `semantic_hash`

```text
semantic_hash = SHA256(semantic_text_version + canonical_semantic_text)
```

Outbox Worker 根据哈希选择操作：

| 变化 | 操作 |
|---|---|
| 新商品 | 生成向量并完整 index |
| 标题/稳定属性变化 | 重新生成向量并完整 index |
| 只有价格/销量/评分/图片/链接变化 | 复用原向量，只更新标量字段 |
| 商品失效 | 标记/删除索引文档，不生成向量 |

### 11.3 批处理

- 同一采集页或小批次统一调用 `encode_documents`。
- OpenSearch 使用 bulk 写入，不逐条 refresh。
- 一个补库阶段结束后统一 refresh，然后再执行混合检索。
- 向量化失败时 MySQL 数据仍保留，Outbox 保持未完成并返回 `partial`，不得假装已可检索。

### 11.4 Mapping 扩展

目标商品文档建议增加：

```json
{
  "category_key": "air_fryer",
  "category_path": ["家用电器", "厨房电器", "空气炸锅"],
  "captured_at": "2026-07-22T12:00:00Z",
  "last_seen_at": "2026-07-22T12:00:00Z",
  "semantic_hash": "sha256...",
  "scope_ids": ["scope_xxx"]
}
```

Mapping变化通过新物理索引和别名原子切换发布，不在现有索引上进行不可逆的临时修改。

## 12. 混合检索更新

### 12.1 召回前过滤

在现有 `platform` 前置过滤基础上，目标查询可增加：

- `category_key` 或本次 `scope_id`；
- 必要的新鲜度边界；
- 商品/Offer活动状态。

这些字段限定本次合法候选域，并同时作用于 BM25 与 KNN。价格、币种、评分、销量和用户属性约束
继续放在 RRF 后的 `post_filter`，不改变固定融合契约。

### 12.2 多平台调用

- `ItemSearch` 对外仍只接受一个平台。
- 多平台需求继续由父 Agent 产生三个同质 `dispatch_tool` 调用。
- 每个 fork 共享完整工具集和 Prompt，使用独立 child thread/checkpoint。
- 三路结果回流父 Agent 时，每路最多保留 10 条候选。
- Provider 补库进度统一发布到根 thread/run，前端只展示一份合并进度。

### 12.3 结果状态

`ItemSearchOutput.status` 扩展或明确为：

| 状态 | 含义 |
|---|---|
| `ok` | 本平台目录和检索完整完成 |
| `partial` | 使用较少候选、陈旧缓存或部分 Provider 结果完成检索 |
| `not_configured` | Provider/OpenSearch/Embedding等必要资源未配置 |
| `error` | 已配置资源执行失败 |
| `cancelled` | 根任务取消，内部工作已停止 |

建议增加公共元数据：

```json
{
  "catalog_status": "fresh|hydrated|partial|stale",
  "catalog_candidate_count": 34,
  "captured_at": "2026-07-22T12:00:00Z",
  "provider_status": "ok",
  "retrieval_rank": 1
}
```

## 13. AG-UI 事件设计

### 13.1 原则

- 继续使用当前统一事件信封：`event/type + thread_id + run_id + timestamp + sequence + data`。
- 标准运行、步骤、工具和文本事件保持不变。
- 商品目录内部子阶段使用 `CUSTOM`，避免把内部服务伪装成新的 LLM 工具。
- 事件必须经过 EventBroker 分配 sequence、缓冲和 WebSocket 广播，支持断线重放。
- 只发布用户可理解的状态和脱敏计数，不发布原始 Prompt、思维链、Token或完整 Provider 响应。
- 每页或每阶段发布一次；高频内部进度按 300～500ms 节流，避免前端抖动和事件洪泛。

### 13.2 事件时序

```text

TEXT_MESSAGE_START

STEP_STARTED think

STEP_FINISHED think

TOOL_CALL_START item_search
TOOL_CALL_ARGS item_search（脱敏参数）

CUSTOM catalog_fetch_progress（每平台/每页）

CUSTOM catalog_normalization_progress
CUSTOM catalog_persistence_progress
CUSTOM catalog_index_progress
CUSTOM hybrid_retrieval_progress
TOOL_CALL_RESULT item_search（压缩结果）
TOOL_CALL_END item_search

STEP_STARTED reflect
...
TEXT_MESSAGE_CONTENT...

```


### 13.4 失败与取消事件

- 单平台失败：发送 `catalog_fetch_progress(status=failed)`，包含稳定错误码和可理解文案，不包含原始异常。
- 部分完成：`catalog_fetch_finished(status=partial)`，列出 `partial_platforms`。
- 全部不可用：外层 `TOOL_CALL_END(status=not_configured|error)`，最终由 Agent决定澄清或失败。
- 用户取消：现有 `TASK_CANCELLED` 是唯一根终态；内部子任务不能再继续发送成功进度。
- `RUN_ERROR` 只用于根任务失败，不能因为一个平台失败就提前终止整个 run。

### 13.5 前端状态与展示

前端 reducer 建议新增临时状态：

```ts
type CatalogProgress = {
  stage: "intent" | "cache" | "fetch" | "normalize" | "persist" | "index" | "retrieve";
  message: string;
  total: number;
  target: number;
  platforms: Record<string, { status: string; accepted: number }>;
};
```

展示要求：

- 提交后立即显示初始化状态，不等模型或Provider返回；
- 展示“正在理解需求”“正在搜索三个平台”“已找到 N 件”等用户语言；
- 不展示内部工具英文名、Provider Token、页游标、堆栈或原始业务码；
- 进度条不得伪装为精确时间百分比，可使用阶段式进度和商品计数；
- 初步候选未完成跨平台筛选前，不将其标记为最终推荐；
- 终态、切换会话或新 run 开始时清理临时进度；
- sequence 去重、断线重放和 replay gap 恢复继续沿用当前机制。

## 14. 任务生命周期与取消传播

目录补库必须属于当前 `thread_id/run_id` 的后台任务：

1. `POST /api/v1/tasks` 仍立即返回 202。
2. RunRegistry 创建根任务并发布 `RUN_STARTED`。
3. AgentLoop/fork/ItemSearch/CatalogHydrationService 继承 ContextVar。
4. Provider请求、数据库事务、Outbox和Embedding定期检查取消状态。
5. 同一thread启动新run时先取消旧run并等待清理。
6. 同一CatalogScope被不同thread请求时，公共singleflight任务与订阅者取消要分离：一个订阅者取消
   不应错误取消仍被其他run使用的公共补库任务；没有订阅者后才允许终止。
7. 成功、失败和取消都通过finally释放平台信号量、singleflight引用和临时资源。

## 18. 验收标准

实现完成必须同时满足：

1. 用户询问一个未建库新品类时，系统先识别品类再调用Provider。
2. 品类不明确时先追问且不会产生Provider调用。
3. 三个平台合计60～100条作为正常工作区间，120条硬停止。
4. 缓存充分的重复请求不再次产生付费搜索。
5. API数据先写MySQL，再通过Outbox进入OpenSearch。
6. 仅标量变化不会重复生成向量。
7. 最终ItemSearch仍使用BM25+BGE-M3+无权重RRF。
8. 一个Provider失败时可返回其他平台真实结果并标记partial。
9. 用户从提交后即可持续看到脱敏、可理解、可重放的进度。
10. 取消能够停止分页、入库、向量化和Agent后续阶段。
11. 自动测试不调用真实付费模型或商品Provider。
12. 未确认数据授权时不得把Provider结果建立为长期公共商品库。

## 19. 风险与待确认事项

| 风险/决策 | 当前处理 |
|---|---|
| Just One API真实单价 | 官方公开接口页未展示具体单价；实施前以控制台/书面信息确认 |
| 数据长期保存和前端展示授权 | 当前未确认；真实长期建库前必须确认 |
| Provider长尾品类质量 | 通过新品类小样本验收，不假设耳机经验自动适用于所有品类 |
| 100条仍可能不足 | 允许在用户明确要求下启动后台扩容，不阻塞首次回答 |
| 100条也可能包含大量重复/配件 | 数量只统计标准化、去重和硬过滤后的有效候选 |
| 抖音分页不稳定 | 串行传递searchId，失败后partial，不阻塞其他平台 |
| CPU Embedding延迟 | 批量编码、semantic_hash复用；必要时部署兼容CUDA环境但不改模型 |
| 多用户重复付费 | scope singleflight、请求账本和新鲜度缓存 |
| 索引不断增长 | 设计陈旧Offer失效、快照生命周期和周期性蓝绿重建 |
| 进度事件过多 | 按页/阶段发送并节流，EventBroker继续使用有界缓冲 |

## 20. 当前实现与目标差距摘要

| 能力 | 当前实现 | 本文目标 |
|---|---|---|
| 品类范围 | 主要为耳机快照 | 按用户意图动态补充任意品类 |
| Provider | 独立耳机采集器，未接Agent主链路 | 通用异步Provider适配层 |
| 候选规模 | 离线固定1000条 | 每次范围60～100条、最多120条 |
| 数据流 | 离线JSONL导入MySQL/OpenSearch | Provider→MySQL→Outbox→OpenSearch在线增量链路 |
| 向量更新 | Outbox商品更新通常重新编码 | semantic_hash控制，标量更新复用向量 |
| 缓存 | 商品索引存在但无查询范围覆盖状态 | CatalogScope覆盖、新鲜度和singleflight |
